# XML / C++ — pilot

**Status:** pilot_ten_selected_search_bounded; incomplete. 10 verified third-party paths, 0 verified standard APIs, 10 verified Docker harnesses.

Seven C++ XML paths pass the namespace-aware catalog control, and OpenSP and cxxtools pass both controls as raw-name paths, with source coverage and AFL++ feedback. Xerces-C++, pugixml, TinyXML, libxml++, gSOAP, OpenSP, cxxtools and RapidXML pass the shared second valid control; TinyXML2 uses a no-processing-instruction variant because it rejects that instruction, while RapidXML's default flags skip it. libxml++ parser-only feedback and native libxml2 parser.c lines are repeatable and input-dependent. The bounded search covered five named format-specific libraries and, on 2026-11-18, a Debian by_inst lookup of C++ XML -dev and framework packages in the same snapshot. TinyXML 2.6.2 (libtinyxml-dev 533) was added from it: a separate Debian source and code base from TinyXML2 (51 of 1,698 normalized non-trivial parser lines, 3.0%, match tinyxml2.cpp in sequence), with namespaces resolved by the adapter as for TinyXML2, pugixml and RapidXML. The pinned upstream 2.6.2 omits Debian's CVE and entity-encoding patches, which concern malformed input and output. Boost.PropertyTree is excluded (84.2% in-sequence overlap of its embedded rapidxml.hpp with RapidXML 1.13, and a framework-wide package); Xalan-C++, XQilla, CodeSynthesis XSD and XMLTooling run over Xerces-C++; Qt XML DOM and libstudxml have no qualifying metric. Other C++ XML packages remain unmeasured. Homebrew install-on-request orders the first three differently and its libxml++ formula is an older ABI; RapidXML has no Homebrew formula. The libxml++ 275 Debian dev installs sum three ABIs, while its matching ABI-5 package has seven. RapidXML's 17 librapidxml-dev installations, none with recent use, are a weak adoption signal and exclude vendored or Boost-embedded copies. Two small valid UTF-8 controls cannot establish complete XML 1.0, DTD/entity, encoding or malformed-input behavior. cxxtools 3.0.0 (libcxxtools-dev 42) has its own XmlReader state machine, but XmlReader never fills the StartElement NamespaceContext, so it is measured as a raw-name path (names as written, xmlns as attributes) against the expat non-namespace oracle used for the C raw-name paths; its package count reflects a general C++ utility library, not XML-specific use. Round 4 (2026-11-18) evaluated gSOAP 2.8.142 (libgsoap-dev 95) through the DOM-only route its DOM manual documents (soapcpp2 -CSL import/dom.h, then an xsd__anyType read with operator>> from a std::istream): gSOAP's own stdsoap2 engine resolves namespaces, both shared valid controls give the exact namespace-aware summary, 1,648 gSOAP lines are covered (147 in dom.cpp) and the controls differ by 126 covered stdsoap2 lines and 84 repeat-stable AFL++ tuples. The generated soapC.cpp is boilerplate from gSOAP's own soapcpp2 tool and is not counted; the fuzz target disables UBSan's alignment check because gSOAP's allocator canary is stored unaligned. Its 95 dev installations count a whole web-services toolkit, not XML-parser use. The same round extended the Debian lookup to every -dev package of the pinned by_inst snapshot whose name or C++ XML role was not covered before (libosp-dev 82, libcutl-dev 3, libace-xml-utils-dev 3, libarabica-dev 2, libacexml-dev 1). OpenSP 1.5.2 (libosp-dev 82, runtime libosp5 10,165) parses both controls with its generic event API in the XML mode doc/xml.htm documents (xml.soc catalog with xml.dcl, SP_CHARSET_FIXED=YES, SP_ENCODING=XML, -wxml, -wno-valid); SGML has no namespaces, so it is measured as a raw-name path against the expat non-namespace oracle. Without a DTD its attribute order follows the attribute lists it implies per element type, which is source order on these controls only. libosp is built as gnu++98 because clang rejects its C++98 access declarations in later modes. libcutl 1.10.0+ds1 (libcutl-dev 3, none with recent use) is the tenth path: cutl::xml::parser, a pull-event layer over Expat's namespace mode, built against the pinned Expat 2.10.0 as Debian builds it; both controls give the exact namespace-aware summary, the cutl layer's covered lines differ by 6 and Expat's by 567, and Expat's hash salt is fixed by a harness-supplied arc4random_buf because cutl exposes no XML_SetHashSalt hook. Its API is documented only in cutl/xml/parser.hxx. A description search of Debian sid -dev packages mentioning XML (131 with installations) found no further C++ parser above three installations: the other C++ rows are Xerces-C++ or libxml2 dependants, XML-RPC, plist, mzML, SCXML or UI libraries and code generators. Arabica (2), ACEXML (1) and the gxmlcpp libxml2 wrapper (2) rank below the tenth path and were not built. The cell reaches its ten-path ceiling; the remaining Debian C++ XML packages are Xerces-C++ or libxml2 dependants, wrappers or code generators, and Qt XML, POCO XML and libstudxml lack a qualifying metric. Ten paths do not establish the ten most-used C++ XML parsers: the bottom five rest on 3 to 95 dev installations. libSBML (libsbml5-dev 121, an SBML library with a documented low-level XML layer over libxml2) was found after the cell closed and is an unresolved lead; if its XML layer qualified it would rank sixth and displace libcutl.
