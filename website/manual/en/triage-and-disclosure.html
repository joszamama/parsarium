After a campaign, crashes/ and hangs/ may contain files. Each one is a lead. Turning a lead into a bug report takes a few steps, and doing them carefully is what makes the report useful to the people who maintain the parser.

1. Reproduce

Run the saved file through the normal harness, outside the fuzzer:

$ parsarium run png c stb runs/stb-afl/afl-out/default/crashes/id:000000,* --results runs/stb-triage

A reproducible crash gives target_nonzero with the error in stderr_tail; a hang gives timeout. Run it a few times. If the result changes between runs, note that: it may depend on memory layout, timing, or the limits of the fuzzing environment rather than the input alone.

2. Reduce

Fuzzer outputs are usually larger than they need to be. A smaller input makes the cause easier to see. For compiled targets, AFL++ includes afl-tmin, which removes bytes while the crash still happens. For any target, you can also reduce by hand with the format in mind: drop chunks, shorten fields, and re-run after each change. Keep the original file next to the reduced one.

3. Deduplicate

A campaign often saves many files for one bug. Group them by where they fail: the top frames of the stack trace for native crashes, the exception type and location for managed languages. Then group again by parser family. If eight PHP packages crash in the same GD function, that is one report to GD.

4. Check the latest release

Parsarium pins releases so results are reproducible. The bug you found may already be fixed upstream. Before reporting, try the input against the latest release and look through the project's issue tracker and changelog.

5. Assess

Describe what the bug allows, as precisely as you can:

  • A memory-safety error in C or C++ (out-of-bounds read or write, use after free) is usually the most serious. AddressSanitizer output helps the maintainer see it.
  • An unhandled exception in a managed language is often a denial of service: the parser stops a request or a worker.
  • A hang or a huge allocation from a small input is a resource problem, also usually a denial of service.
  • A disagreement between parsers matters when two of them sit on the same path, for example a checker and a consumer.

6. Disclose

Look for a SECURITY.md file or a security policy in the project's repository, and use the channel it names. Many GitHub projects accept private vulnerability reports directly. A good report includes the reduced input, the exact release, the command that reproduces it, the observed result, and what you think the impact is. Offer a fix if you can. Give the maintainers time; ninety days is a common default, and most maintainers are glad to hear from someone who did the work to make the problem clear.

For a serious issue, the maintainers or a CVE Numbering Authority such as GitHub can assign a CVE once it is fixed.

Keep a logFor each lead, record the target, the input hash, the status, the stack or exception, the family, the upstream status, and the date you reported it. After a few campaigns this log becomes the most useful file you have.

Key ideas

  • Every file in crashes/ or hangs/ is a lead until it is reproduced outside the fuzzer.
  • Reduce inputs before analysing them; a smaller file makes the cause visible.
  • Deduplicate by failure location, then by parser family.
  • Check the latest upstream release before reporting.
  • Report privately through the project's security policy, with the reduced input, the exact release, and the command to reproduce.

Exercise 8.2Practice

Five crashes were saved in a campaign on several PHP PNG packages. Group them into distinct bugs.

A  nette_utils      Error: imagecreatefromstring() gd_png.c:212 png_read_info
B  league_glide     Error: imagecreatefromstring() gd_png.c:212 png_read_info
C  nette_utils      TypeError: Image::fromString() argument must be string
D  intervention     Error: imagecreatefromstring() gd_png.c:212 png_read_info
E  league_glide     Error: imagecreatefromstring() gd_png.c:340 png_read_image

(These traces are made up for the exercise.)

Hint

Group first by the deepest frame that belongs to the parser, then ask whether the remaining differences are in wrapper code.

Solution

Three groups. A, B, and D fail at the same place in GD (gd_png.c:212): one bug in the shared engine, one report to GD. E fails at a different line in GD: probably a second engine bug. C is a type error in the wrapper's own code, not in the parser: a separate, smaller report to that package. Five files, three reports.
