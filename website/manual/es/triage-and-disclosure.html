Después de una campaña, crashes/ y hangs/ pueden contener archivos. Cada uno es una pista. Convertir una pista en un informe de bug lleva unos cuantos pasos, y hacerlos con cuidado es lo que hace que el informe sea útil para quienes mantienen el parser.

1. Reproducir

Pasa el archivo guardado por el harness normal, fuera del fuzzer:

$ parsarium run png c stb runs/stb-afl/afl-out/default/crashes/id:000000,* --results runs/stb-triage

Un crash reproducible da target_nonzero con el error en stderr_tail; un bloqueo da timeout. Ejecútalo varias veces. Si el resultado cambia entre ejecuciones, anótalo: puede depender de la disposición de la memoria, de los tiempos o de los límites del entorno de fuzzing, y no solo de la entrada.

2. Reducir

Las salidas de un fuzzer suelen ser más grandes de lo necesario. Una entrada más pequeña deja ver mejor la causa. Para targets compilados, AFL++ incluye afl-tmin, que elimina bytes mientras el crash siga ocurriendo. Para cualquier target, también puedes reducir a mano teniendo en cuenta el formato: quita bloques, acorta campos y vuelve a ejecutar después de cada cambio. Guarda el archivo original junto al reducido.

3. Deduplicar

Una campaña suele guardar muchos archivos para un mismo bug. Agrúpalos según dónde fallan: los primeros frames de la traza de pila en crashes nativos, el tipo y la ubicación de la excepción en lenguajes gestionados. Después agrúpalos otra vez por familia de parsers. Si ocho paquetes de PHP fallan en la misma función de GD, eso es un único informe para GD.

4. Comprobar la última versión

Parsarium fija las versiones para que los resultados sean reproducibles. Puede que el bug que has encontrado ya esté corregido en el proyecto original. Antes de informar, prueba la entrada con la última versión y revisa el gestor de incidencias y el changelog del proyecto.

5. Evaluar

Describe lo que permite el bug con la mayor precisión posible:

  • Un error de seguridad de memoria en C o C++ (lectura o escritura fuera de límites, uso después de liberar) suele ser lo más grave. La salida de AddressSanitizer ayuda al mantenedor a verlo.
  • Una excepción no controlada en un lenguaje gestionado suele ser una denegación de servicio: el parser detiene una petición o un proceso.
  • Un bloqueo o una reserva de memoria enorme a partir de una entrada pequeña es un problema de recursos, normalmente también una denegación de servicio.
  • Un desacuerdo entre parsers importa cuando dos de ellos están en el mismo camino, por ejemplo un verificador y un consumidor.

6. Divulgar

Busca un archivo SECURITY.md o una política de seguridad en el repositorio del proyecto, y usa el canal que indique. Muchos proyectos de GitHub aceptan directamente informes privados de vulnerabilidades. Un buen informe incluye la entrada reducida, la versión exacta, el comando que lo reproduce, el resultado observado y el impacto que crees que tiene. Ofrece una corrección si puedes. Da tiempo a los mantenedores; noventa días es un plazo habitual, y la mayoría agradece saber de alguien que se ha tomado el trabajo de dejar claro el problema.

Para un problema grave, los mantenedores o una CVE Numbering Authority como GitHub pueden asignar un CVE una vez corregido.

Lleva un registroPara cada pista, anota el target, el hash de la entrada, el estado, la pila o la excepción, la familia, el estado en el proyecto original y la fecha en que lo comunicaste. Después de unas cuantas campañas, este registro se convierte en el archivo más útil que tienes.

Ideas clave

  • Cada archivo de crashes/ o hangs/ es una pista hasta que lo reproduces fuera del fuzzer.
  • Reduce las entradas antes de analizarlas; un archivo más pequeño deja ver la causa.
  • Deduplica por el lugar del fallo y después por familia de parsers.
  • Comprueba la última versión del proyecto original antes de informar.
  • Informa en privado por el canal que indique la política de seguridad del proyecto, con la entrada reducida, la versión exacta y el comando para reproducirlo.

  1. Reproducir la entrada con parsarium.py run fuera del fuzzer

  3. Pedir un CVE

Todo lo demás depende de poder provocar el comportamiento de forma fiable.

Un parser de Python lanza una excepción no controlada con un archivo manipulado. ¿Cuál es el impacto más probable?

  1. Ejecución remota de código
  2. Corrupción de memoria
  3. Denegación de servicio: la petición o el proceso se detiene

Los lenguajes gestionados protegen la memoria, así que una excepción suele detener el procesamiento en lugar de corromper el estado. Aun así, puede importar en un servicio.

¿Adónde deberías enviar un informe de seguridad sobre un parser?

  1. A una issue pública con el archivo de prueba de concepto
  2. Al canal que indique la política de seguridad del proyecto, normalmente privado
  3. A una publicación en redes sociales mencionando a los mantenedores

La divulgación privada da tiempo a los mantenedores para corregir el problema antes de que sea público.

¿Por qué probar la entrada con la última versión antes de informar?

  1. Puede que el bug ya esté corregido en el proyecto original.
  2. Los informes no admiten versiones fijadas.
  3. Las versiones más nuevas siempre fallan más.

Parsarium fija las versiones para que todo sea reproducible. Una comprobación rápida en el proyecto original nos ahorra tiempo a todos.

Ejercicio 8.1Calentamiento

Toma cualquier campaña del capítulo 7 y pásale afl summary. Si crashes/ o hangs/ no están vacíos, reproduce un archivo con parsarium.py run y rellena el registro descrito arriba. Si los dos están vacíos, pasa el control por run y lee el registro como si fuera una pista.

Pista

Los archivos guardados tienen nombres como id:000000,sig:11,.... Pon la ruta entre comillas en la shell.

Solución

Un crash reproducido aparece como target_nonzero, con el error en stderr_tail; un bloqueo aparece como timeout. Anota el target, el hash de la entrada, el estado, las primeras líneas del error, la familia y la fecha de hoy. Esa fila es el comienzo de tu registro de triaje.

Ejercicio 8.2Práctica

En una campaña sobre varios paquetes de PNG de PHP se guardaron cinco crashes. Agrúpalos en bugs distintos.

A  nette_utils      Error: imagecreatefromstring() gd_png.c:212 png_read_info
B  league_glide     Error: imagecreatefromstring() gd_png.c:212 png_read_info
C  nette_utils      TypeError: Image::fromString() argument must be string
D  intervention     Error: imagecreatefromstring() gd_png.c:212 png_read_info
E  league_glide     Error: imagecreatefromstring() gd_png.c:340 png_read_image

(Estas trazas son inventadas para el ejercicio).

Pista

Agrupa primero por el marco más profundo que pertenezca al parser y después pregúntate si las diferencias que quedan están en el código del wrapper.

Solución

Tres grupos. A, B y D fallan en el mismo punto de GD (gd_png.c:212): un bug en el motor compartido y un informe para GD. E falla en otra línea de GD: probablemente un segundo bug del motor. C es un error de tipos en el propio código del wrapper, no en el parser: un informe aparte, más pequeño, para ese paquete. Cinco archivos, tres informes.
