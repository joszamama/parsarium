WHY PARSERS?

At the boundary.

Parsers turn input in a known format into structure a program can use: pixels, pages, messages, records, and more. Parsarium maps that boundary across languages.

THE QUESTION

What actually parses it?

A package name alone does not show whether it parses a format, which input API to call, or whether a test reaches parser code. Parsarium records those answers with a valid control. Runnable targets add pinned harnesses and feedback.

That makes a parser a useful unit of comparison: the same format can flow through different libraries and language ecosystems, with each path exposing its own entry point, implementation family, and feedback scope.

WHAT A PATH CONTAINS

Evidence you can use.

Each catalog entry has a specific scope. Runnable targets add a reproducible environment and feedback, with limits stated in their guides.

A real input API

Documentation points to the file, string, byte buffer, or stream entry that actually handles the format.

A valid control

A small input produces an observable result for its format. Leads that lack this proof stay outside the verified collection.

Within-cell adoption

Ranks use comparable metrics only within an ecosystem × format cell. Missing metrics remain missing.

A runnable harness

Pinned containers expose one-input replay, corpus replay, and coverage or AFL++ feedback with its measured scope.
