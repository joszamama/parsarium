# Running parser harnesses

Every project accepts a local byte input. The [main CLI](../README.md) lists runnable projects and routes inputs to their pinned container images. Fuzzing runs write under `runs/`, which is ignored by Git.

## One input or an external corpus

```sh
python3 parsarium.py run png c libpng controls/png/red-green.png
python3 parsarium.py replay png c libpng generated/png runs/libpng-replay \
  --generator Fandango --spec png
```

`run` writes a JSON result with the input hash, image ID, exit status, and elapsed time. `ok` means the harness completed; parser acceptance is not inferred from that status. `target_nonzero` and `timeout` are observations requiring replay and triage. Inputs are limited to 1 MiB.

`replay` preserves unique inputs by SHA-256, runs the selected harness, and writes per-input receipts and `summary.json`. Most ecosystems use one-container batch replay when possible; PHP uses individual runs. `--per-case` forces individual replay. Generator metadata can include `--generator-version`, `--spec`, and `--generator-command`.

[Fandango and Fanbase](https://fandango-fuzzer.github.io/Fanbase.html) provide an external generation route. Run `python3 parsarium.py fandango setup` once to install the pinned generator in `.venv/`. `python3 parsarium.py fandango generate` runs `fandango fuzz` with `-F NAME` (Fanbase) or `-f FILE.fan` (local spec), records a `fandango.json` receipt, and with `--replay` or `--prepare-afl` passes the files to `replay` or `afl prepare --seed-dir`. It does not start AFL++. The available Fanbase specs are listed by `fanbase list`. Files generated by hand remain ordinary corpus inputs for the same two commands.

## AFL++

Fully verified projects have an AFL++ overlay; the [current audit](../data/projects-coverage.json) records which paths are ready. The feedback source depends on the project:

| Ecosystem | AFL++ feedback |
| --- | --- |
| C, C++ | Compiled parser edges |
| Rust | Compiled parser edges through afl.rs |
| Go | Covered parser-package statement blocks |
| Java | JaCoCo-covered parser source lines |
| JavaScript | Executed V8 parser source ranges |
| Python | Parser source features or pinned native library edges, as recorded per path |
| PHP | Xdebug-covered parser source lines |

For Go, Java, JavaScript, Python, and PHP, a small instrumented proxy maps parser features into AFL++'s shared feedback map. The parser packages remain unchanged. These bridges are slower than native instrumentation, and their feature and tuple counts are not comparable across ecosystems. Hash collisions in the 64 KiB map are possible. The PHP bridge treats ordinary `Exception` values as parser rejections; PHP `Error` values and process failures remain fatal.

```sh
python3 parsarium.py afl build ascii_ply java jply
python3 parsarium.py afl prepare ascii_ply java jply runs/jply-afl
python3 parsarium.py afl run runs/jply-afl --check
python3 parsarium.py afl run runs/jply-afl --seconds 3600
python3 parsarium.py afl summary runs/jply-afl
```

`afl build` creates the selected local image and verifies its parser coverage. A fresh checkout needs this step before preparation. `afl prepare` copies the project's valid control into `seeds/`, checks the overlay receipt and local image, and writes `plan.json`. Additional inputs enter with repeated `--seed FILE` or `--seed-dir DIRECTORY`. `afl run` checks the plan, image, and seed hashes before starting a time-bounded campaign. `--resume` continues the same `afl-out/` directory. `afl summary` inventories queue, crash, and hang files with hashes and reads AFL++'s `fuzzer_stats`.

C and C++ plans pass `@@` to the verified one-file harness. AFL++ replaces it with each input path; the harness receives the same file argument used by the valid-control check. A manifest can explicitly opt out when its target reads standard input.

Rust targets use `afl::fuzz!`, which reads AFL shared memory and falls back to standard input. Their prepared command runs `/work/afl_fuzzer` without a file argument.

Historical short bridge checks for Go, Java, JavaScript, Python, and PHP have [receipts](../data/afl-campaign-smoke.json). [Differential checks](../data/afl-feedback-differential.json) show input-dependent parser features in those ecosystems. [Recorded plan preflights](../data/afl-plan-smoke.json) cover verified projects at the time each check ran; rerunning a preflight requires its pinned image locally. These checks establish runnable launchers and feedback, not parser safety.

## Ecosystem fuzz engines

Most projects also expose a native fuzz engine: libFuzzer for C, C++, and Rust; Go native fuzzing; Jazzer for Java; Jazzer.js for JavaScript; Atheris for Python; and PHP-Fuzzer for PHP. Paths that require a fresh process per input say so in their manifest and project guide.

```sh
python3 parsarium.py build png javascript pngjs
python3 parsarium.py native prepare png javascript pngjs runs/pngjs-native \
  --duration-seconds 3600
python3 parsarium.py native run runs/pngjs-native --check
python3 parsarium.py native run runs/pngjs-native
```

`native prepare` records the seed hashes, pinned image, engine, duration, and command. `native run` writes `campaign.log` and `campaign.json`. Engine feedback counters differ in meaning and should not be compared between ecosystems.

## Coverage reports

```sh
python3 parsarium.py build svg c libvips
python3 parsarium.py report svg c libvips projects/svg/c/libvips/target/coverage \
  --output reports/libvips --source /work/source=vips-8.18.7.tar.xz
python3 parsarium.py report png c libpng runs/libpng-replay --output reports/libpng-replay
python3 parsarium.py report http11 cpp boost_beast runs/beast-afl \
  --replay-queue --max-queue-inputs 32 --output reports/beast-queue
```

`report` writes `index.html`, `report.json`, and one line view per parser source file under `files/`. The pages are static, need no network, and embed no input bytes. The run must match the project's current verification receipt: changed project files, coverage counts, control output, or replay image IDs stop the report. `--max-report-mib` limits the complete output, including the index and JSON.

A valid-control directory from `build` gives source lines when the coverage is an `llvm-cov export` (C, C++, Rust). Line counts follow the export's segments; files outside the manifest's parser prefixes, such as adapters and harnesses, are excluded and counted. Go coverprofile, Python trace, JavaScript V8, Java JaCoCo, and PHP Xdebug exports also provide line views of executed parser lines when their projects save `executed_lines`. Those exports do not include an unexecuted-line denominator or per-line hit counts, so no percentage is inferred. Projects without a line export report the receipt's covered-line totals, separating the package and underlying parser groups where present. Native binary-edge projects report edges and no source lines. A runtime with native parser function-entry feedback reports baseline, control, and variant function counts without claiming lines or AFL++ edges. Replay directories report input hashes and outcomes; they record no coverage.

For a prepared AFL++ run, `--replay-queue` measures up to 128 saved queue inputs through a verified coverage image. C and C++ LLVM projects merge profiles and generate parser source-line views with input, image, profile, and export hashes; per-function and expansion records are omitted to keep the export bounded. Python projects with installed `.py` parser source replay through Python `trace`; PHP projects with a compatible byte-input harness replay through Xdebug. Both union executed package lines without claiming uncovered lines or a percentage. The trace script, inputs, image, and export are hashed. Native extensions and other coverage modes remain unsupported for queue line views; their AFL feedback and saved-file statistics are still available.

Source text appears only through `--source CONTAINER_DIR=ARCHIVE`, where the archive's SHA-256 equals the manifest's `source_sha256` or `underlying_source_sha256`. Download the pinned release archive listed in the project's source lock before using the example above. `--strip-components` (default 1) removes the archive's top directory. A file whose coverage maps lines beyond its length is shown without text. Without `--source`, line views list counts only.

For Go module ZIPs, `CONTAINER_DIR` may be the manifest's Go package prefix, such as `github.com/go-images/png`. A module ZIP with members under `github.com/go-images/png@v0.2.0/` needs `--strip-components 3` to map `reader.go` to the executed-line view. The ZIP hash must match the project's source pin.

## Run files

| Path | Contents |
| --- | --- |
| `runs/<replay>/inputs/` | Preserved external inputs named by SHA-256 |
| `runs/<replay>/executions/` | Per-input results |
| `runs/<replay>/summary.json` | Corpus and generator metadata |
| `runs/<afl>/plan.json` | Pinned image, seeds, feedback kind, and AFL++ command |
| `runs/<afl>/afl-out/` | AFL++ queue, potential crashes, hangs, and statistics |
| `runs/<afl>/campaign.json` | Execution time, status, and log hash |
| `runs/<afl>/afl-summary.json` | Saved-file inventory and `fuzzer_stats` |
| `runs/<native>/campaign.json` | Native engine execution receipt |
| `<report>/report.json` | Pinned evidence, outcomes, and per-line counts |

Potential crashes and hangs are leads. A saved case requires reproduction and parser-specific triage before any defect claim.
