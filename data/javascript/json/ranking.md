# JAVASCRIPT × JSON: selected parsers (pilot)

10 control-verified third-party paths selected. This bounded pilot verifies ten local byte, stream or text API paths across nine parser families. JSONStream shares the jsonparse tokenizer. A path is an API or package route, not necessarily an independent parser engine.

json5 2.2.3 (MIT, npm integrity and tarball SHA-256 pinned; `lib/` and the README are byte-identical to tag v2.2.3) documents `JSON5.parse(text)` on a JSON5 string and states that JSON5 is a superset of JSON. The adapter decodes the local bytes with a strict UTF-8 `TextDecoder` that keeps a BOM and calls `JSON5.parse` once, with no reviver and no `JSON.parse` fallback; json5 lexes to the end of input and rejects any token after the first value. Its own `lib/parse.js` lexer and parse-state machine builds the value and does not call `JSON.parse`, `eval` or `Function`, so it is a separate family from V8's native `JSON.parse`. The adapter turns the returned value into a type-tagged tree (numbers as IEEE 754 double bits, members in `Object.keys` order); on both valid controls that tree equals one from an independent Python `json` oracle over the same bytes, and the summaries match ([tree receipt](json5-tree-verification.json)). The selection judgement is the grammar: from source reading (not run), json5 also accepts comments, trailing commas, single-quoted strings, unquoted keys, hexadecimal, `Infinity`, `NaN`, leading `+`, extra Unicode whitespace and raw control characters other than CR and LF inside strings, so this path does not reject invalid RFC 8259 input; it is counted for parsing valid JSON. Its download count, the largest in the cell, mainly measures JSON5 configuration-file use (for example through Babel), not strict JSON parsing. V8 marks 497 json5 `lib/` lines on the first valid control, 470 of them in `lib/parse.js`, by the shared line method. The AFL++ bridge, scoped to `/work/node_modules/json5/` so the adapter's tree walk adds no feedback, repeats stably (128/148 and 118/138 features/tuples); the second control changes 18 ranges, all in `lib/parse.js` (sign, zero and exponent number states, string and `\u` escapes, property names), and 18 tuples. On 2026-11-17 the 30-day value was unchanged, and the npm last-week value (2026-11-10 to 2026-11-16) was 327,119,493, first on that window as well.

jsonparse's README documents no API. Its `new Parser()`, `onValue` and `write(chunk)` call pattern comes from the packaged example and tests at the tarball's gitHead. The parser has no `end()` call and accepts a stream of concatenated values, so the adapter writes the whole local Buffer once and then requires exactly one `onValue` with an empty stack, no open container, and the tokenizer back in its START state. From source reading (not run on such inputs), numbers are any run of digits, `.`, `e`, `E`, `+` and `-` checked only by `Number()`, so leading zeros are not rejected, and integer digit strings that do not round-trip through `Number` are emitted as strings. JSONStream 1.3.5 is a separate package API path over jsonparse 1.3.1 and through 2.3.8, all pinned by npm integrity and tarball SHA-256. Its own `index.js` filters and emits roots; jsonparse tokenizes and builds values. The README says an empty path emits no data, while the pinned code and packaged test emit one completed root; the adapter follows that test. The private parser has no end-of-input completeness check, so a trailing unfinished token or open container after one completed root can go undetected. V8 covers 48 JSONStream source lines, 293 jsonparse lines, and 76 through lines on the first valid control. The 17 changed AFL source ranges and tuples between controls are all in jsonparse; JSONStream own source features are identical. It is counted as a package path, not another parser engine ([feedback report](jsonstream-afl-feedback.json)).

@humanwhocodes/momoa 3.3.13 (Apache-2.0, npm integrity and tarball SHA-256 pinned) documents `parse(text)` on a string, with `"json"` as the default mode. The adapter reads the local bytes, decodes them with a strict UTF-8 `TextDecoder` that keeps a BOM, and calls `parse(text, {mode: 'json'})` once; momoa throws on any token after the first value. The bundled `dist/momoa.js` holds its own character-level tokenizer and recursive-descent parser and does not call `JSON.parse`. The summary is built from momoa's AST nodes rather than `evaluate()`, and an independent Python `json` summary of the same control bytes gives the same result. V8 marks 1,590 `dist/momoa.js` lines on the first valid control by the shared line method, which counts every non-blank line inside an executed range, so comments in the module body count. The AFL++ bridge repeats stably (126/146 and 111/131 features/tuples); the second control changes 17 ranges, all in `dist/momoa.js` (string escape and `\u` handling, negative and fractional numbers, line tracking), and 17 tuples. On 2026-11-17 the 30-day value was unchanged, and the npm last-week value (2026-11-09 to 2026-11-15) was 4,871,887, above bfj's 4,518,652, so the rank order holds on both windows.

json-bigint 1.0.0 has a documented `JSONbig.parse(text)` string API. The adapter decodes local bytes as strict UTF-8 and tags the returned values without calling native `JSON.parse` on the input. The release's `lib/parse.js` credits Crockford's public-domain `json_parse.js`; its `bignumber.js` dependency represents long numeric tokens and is not the JSON syntax parser. Both valid controls have exact type-tagged trees, with only safe JavaScript Numbers. Source reading shows that the default parser chooses BigNumber for a finite numeric token whose string has more than 15 characters; those controls do not test that branch. V8 records 293 executed lines in `lib/parse.js` on the first control. The parser-only AFL++ bridge repeats stably: the object and array controls produce 50 and 43 parser ranges, respectively, with seven changed ranges and seven changed AFL++ tuples ([scoped receipt](json-bigint-feedback-differential.json)). The saved 30-day download metric places it third among verified paths; it is not a claim about JSON-specific call frequency.

jsonc-parser 3.3.1 documents `parseTree(text, errors, options)` and warns that its parser is fault tolerant. The adapter decodes local bytes as strict UTF-8, sets `disallowComments: true`, `allowTrailingComma: false`, and `allowEmptyContent: false`, rejects any reported error, and projects its AST into an exact type-tagged tree. These are the package's own scanner and tree parser, not V8 `JSON.parse`. Both valid controls match the independent Python JSON oracle. V8 records 300 executed lines in `lib/umd/impl/parser.js` and 317 in `scanner.js` on the first control. The parser module takes the same source ranges on these two inputs, while the scanner differs; the AFL++ bridge therefore scopes feedback to `scanner.js`. Repeated valid-control probes are stable: 79 and 68 scanner ranges, with 11 differing ranges and 11 differing AFL++ tuples ([scoped receipt](jsonc-parser-feedback-differential.json)). The controls contain no comments, trailing commas, duplicate keys, or unsafe numbers, so they do not establish behavior outside that valid scope.

lossless-json 4.3.3 has a documented `parse(text)` API. The adapter strictly decodes local UTF-8 bytes and traverses the package result without using native `JSON.parse` on the input. The package builds its own values through `lib/esm/parse.js`; numeric source spellings survive as `LosslessNumber.value`, including `-0.25e1` and `2.5e-1` in the two pinned controls. The type-tagged results match an independent Python JSON oracle with exact numeric lexemes. V8 covers 252 own parser lines, and three fresh repeats per valid control yield stable parser-only AFL++ maps with eight different source-range features and eight different tuples ([scoped receipt](lossless-json-feedback.json)). Downloads include non-parser use and transitive adoption.

## Standard API (unranked)

| API | Runtime | Parser family |

| [JSON.parse(text)](https://tc39.es/ecma262/#sec-json.parse) after strict UTF-8 [TextDecoder](https://nodejs.org/download/release/v26.10.0/docs/api/util.html#class-utiltextdecoder) | Node.js 26.10.0 | V8 native JSON.parse |

`JSON.parse` takes a string, so the adapter decodes bytes first. V8 implements it natively. Its AFL++ target is a Node.js 26.10.0 build from the official source where only V8's `json-parser.cc` is instrumented; it runs the same adapter on one file. Map entries are parser coverage points, not lines, and come from a source build rather than the pinned official binary ([AFL++ receipt](../../../fuzzing/afl-native/json/javascript/stdlib_json_parse/verification.json)).
