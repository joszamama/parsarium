**hickory-proto 0.26.3** (MIT OR Apache-2.0) parses local bytes with `hickory_proto::op::Message::from_vec(buffer: &[u8]) -> Result<Message, DecodeError>`. Both controls match the oracle summary. The response control covers 479 library lines in 55 files. AFL++ feedback repeats 3 times per control; response and query give 703/446 parser features and 285/178 AFL++ tuples, differing by 259 features and 107 tuples ([receipt](hickory-proto-feedback-differential.json)). Own pure-Rust decoder (serialize/binary/decoder.rs, op/message.rs, rr/record.rs, rr/domain/name.rs). trust-dns-proto is the same project under its earlier crate name. The crate drops the reserved Z bit, so z reports AD and CD only.

**simple-dns 0.13.1** (MIT) parses local bytes with `simple_dns::Packet::parse(data: &[u8]) -> Result<Packet, SimpleDnsError>`. Both controls match the oracle summary. The response control covers 310 library lines in 46 files. AFL++ feedback repeats 3 times per control; response and query give 434/272 parser features and 182/120 AFL++ tuples, differing by 162 features and 62 tuples ([receipt](simple-dns-feedback-differential.json)). Own pure-Rust decoder, used by mdns-sd-style service discovery crates (simple-mdns, iroh); no code from hickory-proto. It exposes AD and CD as packet flags but not the reserved Z bit, so z reports AD and CD only. A and AAAA addresses are stored as u32/u128; the harness prints them with std::net.

**domain 0.12.3** (BSD-3-Clause) parses local bytes with `domain::base::Message::from_slice(slice: &[u8]) -> Result<&Message<[u8]>, ShortMessage>`. Both controls match the oracle summary. The response control covers 606 library lines in 65 files. AFL++ feedback repeats 3 times per control; response and query give 692/419 parser features and 32/28 AFL++ tuples, differing by 273 features and 4 tuples ([receipt](domain-feedback-differential.json)). Own pure-Rust decoder by NLnet Labs (the authors of ldns, Unbound and NSD), a separate Rust code base from the selected C ldns path. from_slice checks the header length; the question and record sections are parsed lazily when the harness iterates them (records read as AllRecordData with ParsedName). It keeps the Z, AD and CD bits. Built with default-features = false and std (only the rand default is dropped). Its parser is generic over octet types, so most of it is monomorphized into the (uninstrumented) harness crate: the scoped AFL++ map keeps only 32/28 tuples (4 differing) although LLVM source regions differ by 273.

**dns-parser 0.8.0** (MIT OR Apache-2.0) parses local bytes with `dns_parser::Packet::parse(data: &[u8]) -> Result<Packet, Error>`. Both controls match the oracle summary. The response control covers 250 library lines in 29 files. AFL++ feedback repeats 3 times per control; response and query give 351/181 parser features and 129/79 AFL++ tuples, differing by 170 features and 52 tuples ([receipt](dns-parser-feedback-differential.json)). Own pure-Rust decoder (tailhook), the parser behind older mDNS crates; no code from hickory-proto or simple-dns. The header keeps AD and CD but not the reserved Z bit, so z reports AD and CD only. ResourceRecord has no numeric type field: the harness maps the decoded RData variant (A, AAAA, CNAME, NS, PTR, MX) to its type number. Last release 2018 (edition 2015 crate).

**dns-message-parser 0.9.0** (BSD-3-Clause) parses local bytes with `dns_message_parser::Dns::decode(bytes: Bytes) -> DecodeResult<Dns>`. Both controls match the oracle summary. The response control covers 338 library lines in 86 files. AFL++ feedback repeats 3 times per control; response and query give 509/276 parser features and 252/140 AFL++ tuples, differing by 233 features and 114 tuples ([receipt](dns-message-parser-feedback-differential.json)). Own pure-Rust decoder (LinkTed); no code from hickory-proto, domain or simple-dns. Flags keep AD and CD but not the reserved Z bit, so z reports AD and CD only. Records decode into typed structs; A and AAAA structs carry no class because the decoder accepts those types only in class IN (any other class is a decode error), so the harness reports class 1 for them. The harness copies the local bytes into a bytes::Bytes buffer for the documented decode entry point.

**rustdns 0.7.0** (Apache-2.0) parses local bytes with `rustdns::Message::from_slice(buf: &[u8]) -> io::Result<Message>`. Both controls match the oracle summary. The response control covers 221 library lines in 9 files. AFL++ feedback repeats 3 times per control; response and query give 350/203 parser features and 218/150 AFL++ tuples, differing by 149 features and 68 tuples ([receipt](rustdns-feedback-differential.json)). Own pure-Rust decoder (bramp); no code from hickory-proto or the other selected crates. Built with default-features = false, so the DNS clients (UDP/TCP/DoH) and zone-file parser are not compiled; the message parser is part of the base crate. It keeps the Z, AD and CD bits. TTLs are Durations printed in whole seconds.

**rsdns 0.23.0** (MIT OR Apache-2.0) parses local bytes with `rsdns::message::reader::MessageIterator::new(buf: &[u8]) -> Result<MessageIterator>; header(), questions(), records()`. Both controls match the oracle summary. The response control covers 463 library lines in 33 files. AFL++ feedback repeats 3 times per control; response and query give 607/386 parser features and 259/108 AFL++ tuples, differing by 223 features and 151 tuples ([receipt](rsdns-feedback-differential.json)). Own pure-Rust decoder in a DNS client library; built without any net-* feature, so no client code is compiled. The records iterator tags every record with its section. rsdns exposes no Z, AD or CD flag (the Z getter is test-only), so z is reported as 0.

**packet-dissector-dns 0.6.3** (MIT OR Apache-2.0) parses local bytes with `packet_dissector_dns::DnsDissector.dissect(data: &[u8], buf: &mut DissectBuffer, offset: 0)` (the `packet_dissector_core::dissector::Dissector` trait). Both controls match the oracle summary. The response control covers 381 library lines in 4 files. AFL++ feedback repeats 3 times per control; response and query give 549/339 parser features and 168/98 AFL++ tuples, differing by 210 features and 70 tuples ([receipt](packet-dissector-dns-feedback-differential.json)). Own pure-Rust zero-copy dissector from the packet-dissector project (higebu); no code from the other selected crates. The harness calls the DNS dissector directly on the message bytes, not through the Ethernet/IP/UDP registry, so no link-layer frame is involved. The dissector validates every name, including the CNAME and MX targets inside RDATA, and stores names as wire byte ranges; the harness renders them with the crate's public `write_dns_name` FormatFn (which follows compression pointers) and adds the trailing dot. A and AAAA arrive as address field values printed with std::net; Z, AD and CD are separate header fields. The metric is the sub-crate's own count; its README says it is normally used through the packet-dissector crate's dns feature.

**hns-dns-wire 0.2.2** (MIT OR Apache-2.0) parses local bytes with `hns_dns_wire::Message::parse(message: &[u8]) -> Result<Message, Error>`. Both controls match the oracle summary. The response control covers 291 library lines in 1 file. AFL++ feedback repeats 3 times per control; response and query give 502/313 parser features and 156/103 AFL++ tuples, differing by 189 features and 55 tuples ([receipt](hns-dns-wire-feedback-differential.json)). Own single-file pure-Rust decoder from the hns-dane-engine project (Handshake DNSSEC/DANE), with no dependencies and no code from the other selected crates. It is strict: it rejects forward, cyclic and out-of-message compression pointers and a set reserved Z bit, and it exposes AD but not CD, so the harness reads z from the parsed Flags::bits() word. Names are printed by the crate's own Display (lower case, absolute); A and AAAA are std::net addresses. Found by the round-3 crates.io searches sorted by recent downloads.

**oxidns-proto 0.1.8** (MIT OR Apache-2.0) parses local bytes with `oxidns_proto::Message::from_bytes(bytes: &[u8]) -> Result<Message>`. Both controls match the oracle summary. The response control covers 526 library lines in 22 files. AFL++ feedback repeats 3 times per control; response and query give 709/499 parser features and 280/178 AFL++ tuples, differing by 212 features and 104 tuples ([receipt](oxidns-proto-feedback-differential.json)). Own pure-Rust message model and wire codec split out of the OxiDNS server. Its type names follow the Hickory API style (RData, DNSClass, MessageType), but only 588 of its 5,987 distinct non-comment source lines (9.8%) also occur in hickory-proto 0.26.3, so it is counted as its own decoder. The header keeps AD and CD but not the reserved Z bit, so z reports AD and CD only. Names come from the crate's Name::to_fqdn() (canonical lower case with the trailing dot); A and AAAA are std::net addresses. flex-dns (300) ranks above it but needs a nightly-only compiler feature (see the remaining leads).

- **smoltcp**: smoltcp::wire::dns (Packet, Question, Record::parse) is a documented public wire API, but RecordData decodes only A and AAAA: CNAME stays as the raw (possibly compressed) name bytes and MX falls into Other(type, raw bytes), with no exported decoder for names inside RDATA, so the control's CNAME and MX answers would have to be decoded by the harness. The crate is a TCP/IP stack; its count covers all protocols.
- **webrtc-mdns**: The public module webrtc_mdns::message (a Rust port of Go's golang.org/x/net/dns/dnsmessage via Pion mDNS, with typed A/AAAA/CNAME/MX/NS/PTR/SOA/SRV/TXT bodies) has Message::unpack(&mut self, &[u8]), but neither the README (which documents only the mDNS conn) nor any rustdoc comment documents it: every item in message/ carries plain // comments, so docs.rs shows bare signatures. Same rule as PHP yswery/dns: a public but undocumented entry point stays a lead. Family would be the x/net dnsmessage port already selected in Go.
- **dnssector**: DNSSector::parse validates the whole message (including compressed names inside CNAME/MX RDATA) and the RR iterators return owner name, type, class, TTL and A/AAAA addresses, but other RDATA only as raw bytes (RawRRData::Data). The crate has no public API returning the CNAME target, MX preference or MX exchange as values (Compress::copy_uncompressed_name yields wire-format labels only), so the control's CNAME and MX answers would have to be decoded by the harness.
- **microdns**: Minimal resolver library: its public helpers parse the header and answer records, but the question section is only skipped (skip_question) and its name, type and class are not returned, and authority/additional handling is left to callers. The control's question cannot be reported from the library.
- **proxima-protocols**: The dns module (proxima_protocols::dns) is a documented sans-IO RFC 1035 parser, but its own module docs state that RDATA is decoded only for A, AAAA and CNAME/NS/PTR and that other types are kept as raw bytes, so the control's MX answer (preference and exchange) would have to be decoded by the harness.
- **geiserx_ts_dns_wire**: MagicDNS responder codec: decode_query(&[u8]) decodes only the first question of an incoming query and the crate otherwise only encodes responses, so the response control's answers cannot be reported from the library.
- **dns-protocol**: Message::read decodes the header, questions and record headers, but ResourceRecord::data() returns RDATA as raw bytes and the crate exports no decoder for (compressed) names inside RDATA, so the control's CNAME and MX targets would have to be decoded by the harness.
- **mdns-proto**: Sans-I/O mDNS state machines with a wire reader, but its resource_type module documents that only CNAME and PTR name-bearing RDATA are parsed; MX and the other RFC 1035 name-bearing types map to Unknown and are dropped by callers, so the control's MX answer cannot come from the library.
- **dns_parse**: parse(Bytes) returns only the answer records (it skips the question section and returns no header, question, authority or additional data), so most of the control summary cannot come from the library.
- **flex-dns**: Documented no_std parser (DnsMessage::new(buffer) with questions()/answers()/name_servers()/additionals() readers) that ranks next by metric, but the crate root enables #![feature(generic_const_exprs)], an incomplete nightly-only feature. Parsarium's pinned Rust 1.99.1 stable image and the generated cargo-afl overlay have no nightly path (it builds only with RUSTC_BOOTSTRAP=1, which the overlay builder does not set), so the runnability gate is not met; not attempted further.
- **dnsparse**: Message exposes the header, questions and answers, but Answer::rdata() is raw bytes with no decoder for names inside RDATA, and there is no accessor for the authority or additional sections.

## Checked, excluded or recorded separately

- **trust-dns-proto** (excluded): Predecessor of the already selected hickory-proto: trust-dns-proto 0.23.2 is the last release of the same project before the rename to hickory-proto (0.24). It passed both DNS controls and the full gate, but the decoder code is largely the same: 72% of trust-dns-proto's distinct non-test lines in serialize/binary (BinDecoder), 83% in rr/domain (name decoding) and 53% in op (Message/Header) are identical in hickory-proto 0.26.3 (44% over the whole crate, which also carries resolver/runtime code). Shared family with a stronger selected path; not counted. Evidence: data/rust/dns/trust-dns-proto-demoted.json.
- **mdns-sd** (excluded): mDNS service-discovery daemon; its message parser is not a documented public bytes API.
- **rama-dns** (excluded): DNS support for the rama framework built on hickory-resolver (Cargo dependency); it exposes resolver services, not its own parser for caller-supplied message bytes.
- **hickory-net** (excluded): Networking half of the Hickory DNS 0.26 split (clients, transports, runtime); message decoding stays in the selected hickory-proto, which it depends on. No own parser.
- **rtc-mdns** (excluded): Sans-I/O successor of webrtc-mdns in the same webrtc-rs project; its message module is pub(crate) (src/lib.rs), so there is no public bytes API. 82.7% of its distinct message/ source lines also occur in webrtc-mdns 0.17.3.
- **tendns** (excluded): Encrypted-TXT discovery library and DNS server built on hickory-proto/hickory-resolver/hickory-server (Cargo dependencies); no own message parser.
- **packet-dissector-mdns** (excluded): mDNS (RFC 6762) wrapper of the selected packet-dissector-dns: the mDNS reinterpretation (dissect_as_mdns) lives in packet-dissector-dns itself, so this crate adds no own DNS message parser.
- **idns** (excluded): Racing DNS resolver: it sends queries and parses only answer records per queried type (parse/a.rs, aaaa.rs, mx.rs, spf.rs); no documented API for a caller-supplied whole message. dns_parse (a lead) reuses its Answer type.
- **dyns** (excluded): DNS discovery and resolver support for DHTTP applications (resolvers, publishers, mDNS); network API with no documented parser for caller-supplied message bytes.
- **dope-dns** (excluded): Bounded discovery client; its wire module (packet, response) is private to the crate (lib.rs exports config, host, lookup, query, storage, topology), so there is no public bytes API.
- **dns-parser-revived** (excluded): Fork of the selected dns-parser: 728 of its 1,013 distinct non-comment source lines (71.9%) also occur in dns-parser 0.8.0.
- **dns-parser-joe** (excluded): Fork of the selected dns-parser: 708 of its 855 distinct non-comment source lines (82.8%) also occur in dns-parser 0.8.0.
- **dnsclient** (excluded): DNS client and stub resolver (sync, Tokio, Smol) built on dnssector (re-exported); its own API sends queries and returns addresses, with no own parser for caller-supplied message bytes.
- **pktkit** (excluded): L2/L3 packet toolkit; its virtual client's DNS helper parse_response(data, query) returns only the IP addresses that answer a matching query, not a decoded message.
