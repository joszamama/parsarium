# RustyXML 0.3.0: feedback audit

The pinned [RustyXML release](https://static.crates.io/crates/RustyXML/RustyXML-0.3.0.crate) has SHA-256 `8b5ace29ee3216de37c0546865ad08edef58b0f9e76838ed8959a84a990e58c5`. Its MIT and Apache-2.0 license files have SHA-256 `e36cdd9db3545a42292211f451d53db2d9a4a287fcdcaf06b2be93c3ec7c2430` and `a60eea817514531668d7e00765731449fe14d059d3249e0bc93b36de45f759f2`. The source's `src/parser.rs` says this parser derives from OFXMLParser in ObjFW, with the original author's permission. The crate's library name is `xml`; it is unrelated to the selected `xml` (xml-rs) crate.

## Controls and source coverage

The documented `xml::Parser::new(); feed_str(&str)` API yields namespace-aware SAX-like events. The [harness](../../../projects/xml/rust/rustyxml/src/lib.rs) decodes the local bytes as UTF-8, feeds the text, and iterates the events. RustyXML resolves element and attribute prefixes itself and keeps `xmlns` attributes in `StartTag.attributes`; the harness counts those as declarations. `StartTag.attributes` is a HashMap, so each element's attributes are sorted by (namespace, local name), which equals document order on both controls. The summaries for [catalog-ns.xml](../../../controls/xml/catalog-ns.xml) and [order-default-ns.xml](../../../controls/xml/order-default-ns.xml) match the Expat oracle exactly. A Rust 1.99.1/Linux arm64 Docker build with LLVM source coverage covers 285 RustyXML lines on the catalog control (266 in `src/parser.rs`) and 307 on the order control (281 in `src/parser.rs`).

## Cause of the earlier AFL++ variance

An earlier whole-binary cargo-afl 0.18.2 build varied between identical runs, and a RustyXML-only SanitizerCoverage build still gave 621 edges once and 613 edges nine times on the order control. The source explains why. `Parser` keeps namespace bindings as `Vec<HashMap<String, String>>` and looks up every element and attribute prefix through them (`namespace_for_prefix`); each start tag also builds a `HashMap<(String, Option<String>), String>` of attributes. These are std `HashMap`s with `RandomState`, whose SipHash keys come from `getrandom(2)` once per process. The hashbrown probe and insert-slot code for these maps is monomorphized into the RustyXML crate and carries its SanitizerCoverage guards. Different keys put the same entries in different buckets; the inferred effect is occasional extra probe steps or control-byte matches, which add a few edges. Fixing the keys (below) removed the variance. LLVM source-line segment maps were identical across repeated runs because these paths are inside inlined library code, not in different RustyXML source lines.

The current overlay instruments only the RustyXML crate (`afl_instrumented_crates: ["xml"]`; harness, serde_json and AFL runtime crates carry no guards). With per-process random keys, repeated `afl-showmap` runs on that image still varied. On the catalog control, 26 of 30 runs gave 667 edges and the others gave 668, 668, 669 and 672. On the order control, 29 of 30 runs gave 733 edges and one gave 738. Ten guards varied on the catalog control; the five that varied on the order control are among them.

## Deterministic replay setting

The binary resolves `getrandom` through a weak glibc dynamic symbol. The overlay compiles [fixed_getrandom.c](../../../fuzzing/afl-native/xml/rust/rustyxml/fixed_getrandom.c), which returns constant bytes, and sets `AFL_PRELOAD=/work/fixed_getrandom.so`, so every target process starts with the same HashMap keys. RustyXML source and the harness are unchanged. The [overlay build](../../../fuzzing/afl-native/xml/rust/rustyxml/build.py) checks that the base replay output for both controls is identical with and without the shim. With fixed keys, ten `afl-showmap` repeats per control are identical: 668 edges on the catalog control and 733 on the order control, with 59 and 124 edges unique to each. A further 20 repeats per control on an image with the same binary and shim were also identical (668 and 733).

## Limits

The shim fixes only the process-start keys. std increments the key for each new `RandomState`, so successive iterations of a persistent-mode afl-fuzz campaign still hash with different keys, and campaign stability can be below 100%. The receipt establishes repeatable per-process feedback on the two valid controls only. RustyXML's README lists incomplete error checking, so these controls do not establish strict XML 1.0 well-formedness checking, DTD handling or non-UTF-8 input. No malformed input or fuzzing campaign was run.
