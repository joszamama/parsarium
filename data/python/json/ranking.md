# Python × JSON: pilot ranking

Ten third-party paths are control verified, reaching the ten-path ceiling. Seven came from targeted documentation leads; json5, dirtyjson and hjson came from the bounded [PyPI Simple index name search](registry-snapshot.json) (six project-name queries, first 100 alphabetical hits each) with a top-15,000 download list used only to pick plausible high-adoption leads. Ten leads remain unresolved, all with fewer downloads than hjson, the tenth selected path. python-rapidjson and pysimdjson passed every gate but were displaced under the ten-path ceiling by dirtyjson and hjson (see below). This is not a claim about the definitive most-used JSON parsers.

The comparable within-cell signal is [PyPI Stats](https://pypistats.org/api/) `last_month` package downloads excluding known mirrors, observed 2026-11-17 around 02:24 UTC for the first nine and again at 15:04 UTC for every lead in the [registry snapshot](registry-snapshot.json); all nine earlier values were identical in the second capture. It measures adoption of entire packages, including transitive installs and uses unrelated to JSON parsing. Unverified leads are recorded in [leads.json](leads.json) but are not ranked as verified parsers.

The standalone `jiter` package is a distinct verified package API path, not an independent parser: it shares Pydantic's Jiter Rust parser family (0.19.0 standalone, 0.18.0 inside pydantic-core). Their package download metrics remain separate. The [jiter receipt](jiter-valid-feedback.json) records exact valid-control type-tagged trees and repeated, input-dependent feedback in Jiter's own Rust parser source. All ten selected paths have pinned container controls, parser-scoped coverage, and AFL++ feedback. The [Pydantic native receipt](pydantic-valid-feedback.json) checks repeated, input-dependent Jiter source regions on two valid controls. The [orjson receipt](orjson-valid-feedback.json) records 114 differing Rust deserializer features and AFL++ tuples between those controls; vendored yyjson C syntax-parser source is outside that coverage. The [ijson receipt](ijson-valid-feedback.json) records stable valid-control differential in its own C extension and pinned YAJL C tokenizer. Its source-built embedded YAJL -O0 route differs from the official Linux wheel’s linkage and optimisation, and other backends are untested. The [msgspec receipt](msgspec-valid-feedback.json) records stable input-dependent feedback from its own `_core.c` decoder, including 35 differing features in the JSON decoder section. The source build uses clang -O0 while the published wheel is built with GCC; only untyped `type=Any` decoding is tested. The [ujson receipt](ujson-valid-feedback.json) checks that `ujson.loads` on bytes and on text gives the exact type-tagged tree of an independent CPython `json` oracle for both controls, and records stable differential feedback in `decode.c` and double-conversion C++. Duplicate keys (last wins), integer overflow to arbitrary precision and the non-RFC `NaN`/`Infinity` tokens are documented from source only. The simplejson metric is retained in the dated [lead snapshot](leads.json). The [json5 receipt](json5-valid-feedback.json) checks that `json5.loads` on bytes and on text, and `json5.load` on a `BytesIO` stream, give the exact type-tagged CPython `json` oracle tree for both controls; the standard `json` module is blocked during those runs and json5 never imports it. Docker line tracing covers 668 json5 lines (596 in the glop-generated `parser.py`, 72 in `lib.py`). Three runs per control give identical feedback, and the controls differ by 27 `parser.py` lines and 27 AFL++ tuples. json5 is a JSON5 superset parser: it accepts comments, unquoted keys, trailing commas, single-quoted strings, hexadecimal numbers and Infinity/NaN, so it does not reject non-RFC 8259 input, and its downloads mainly reflect JSON5 configuration use. Duplicate keys (last wins by default) and number conversion through Python `int`/`float` come from source, not tests. The [dirtyjson receipt](dirtyjson-valid-feedback.json) and [hjson receipt](hjson-valid-feedback.json) check that `loads` on bytes and on text, and `load` on a `BytesIO` stream, give the exact type-tagged CPython `json` oracle tree for both controls, with the standard `json` module blocked during those runs; neither package imports it. Docker line tracing covers 156 dirtyjson lines (129 in `loader.py`, 23 in the `attributed_containers.py` result types) and 159 hjson lines (152 in `decoder.py`). Three runs per control give identical feedback; the controls differ by 14 dirtyjson lines and 14 AFL++ tuples (9 in `loader.py`), and by 4 hjson `decoder.py` lines and 4 tuples. Both are separate code bases descended from the simplejson pure-Python decoder: dirtyjson calls its loader a fairly drastic rewrite of the simplejson loader and ships simplejson's license, and hjson says it is based on simplejson. With the selected simplejson path they share one lineage, not three independent parsers. Both accept non-RFC 8259 input: dirtyjson is a lenient decoder (comments, unquoted keys, single quotes, trailing commas) that returns `dict` and `list` subclasses carrying source positions, and hjson parses the Hjson superset and returns `OrderedDict` objects. Number conversion through Python `int`/`float` and last-wins duplicate keys come from source, not tests. The [CPython `json` standard API](standard.json) is recorded separately, without a third-party popularity rank.

The Pydantic and jiter LLVM exports warned about mismatched profile data in 99 and 16 whole-extension functions respectively. Their coverage claims are limited to the scoped Jiter regions recorded in the verification receipts; complete extension coverage is not established.

## Displaced by the ten-path ceiling

[python-rapidjson](https://python-rapidjson.readthedocs.io/en/latest/load.html) 1.26 (4,066,455) and [pysimdjson](https://github.com/TkTech/pysimdjson/blob/98a6f9a84bfc0620cf8b5c450d22b8eeae313bfd/docs/native.rst) 8.0.0 (679,340) passed every gate as selected paths: both valid controls equal to the CPython `json` oracle, a pinned container control, parser-source coverage, and stable input-dependent AFL++ feedback in RapidJSON `reader.h` and the simdjson arm64 kernel. Once dirtyjson and hjson were verified with more downloads, they rank eleventh and twelfth and fall outside the ten-path ceiling. As in the original matrix, each project directory must be a selected catalog row, so their project, overlay, verify-script and test files were removed; their full catalog rows and verification records are kept in [ceiling-displaced.json](ceiling-displaced.json) and their [python-rapidjson](python-rapidjson-valid-feedback.json) and [pysimdjson](pysimdjson-valid-feedback.json) receipts stay in this cell.

[json-repair](https://pypi.org/project/json-repair/0.64.9/) 0.64.9 (43,691,294) is excluded rather than ranked. On valid input its documented default returns the standard `json.loads` result, so it is the CPython `json` family there. Its own repair parser runs only with `skip_json_loads=True`, which the pinned README documents for input already known to be invalid. That use is outside this valid-control gate. pyjson5, json-stream and json-stream-rs-tokenizer were not run because their downloads are below hjson's.
