# Python × JSON: pilot ranking

Ten third-party paths are control verified, reaching the ten-path ceiling. The first nine came from targeted documentation leads; json5 came from the bounded [PyPI Simple index name search](registry-snapshot.json) (six project-name queries, first 100 alphabetical hits each) with a top-15,000 download list used only to pick plausible high-adoption leads. Thirteen leads remain unresolved, and several of them (json-repair, dirtyjson, hjson, pyjson5, json-stream) have more downloads than pysimdjson, so this is not a claim about the definitive most-used JSON parsers.

The comparable within-cell signal is [PyPI Stats](https://pypistats.org/api/) `last_month` package downloads excluding known mirrors, observed 2026-11-17 around 02:24 UTC for the first nine and again at 15:04 UTC for every lead in the [registry snapshot](registry-snapshot.json); all nine earlier values were identical in the second capture. It measures adoption of entire packages, including transitive installs and uses unrelated to JSON parsing. Unverified leads are recorded in [leads.json](leads.json) but are not ranked as verified parsers.

The standalone `jiter` package is a distinct verified package API path, not an independent parser: it shares Pydantic's Jiter Rust parser family (0.19.0 standalone, 0.18.0 inside pydantic-core). Their package download metrics remain separate. The [jiter receipt](jiter-valid-feedback.json) records exact valid-control type-tagged trees and repeated, input-dependent feedback in Jiter's own Rust parser source. All ten selected paths have pinned container controls, parser-scoped coverage, and AFL++ feedback. The [Pydantic native receipt](pydantic-valid-feedback.json) checks repeated, input-dependent Jiter source regions on two valid controls. The [orjson receipt](orjson-valid-feedback.json) records 114 differing Rust deserializer features and AFL++ tuples between those controls; vendored yyjson C syntax-parser source is outside that coverage. The [ijson receipt](ijson-valid-feedback.json) records stable valid-control differential in its own C extension and pinned YAJL C tokenizer. Its source-built embedded YAJL -O0 route differs from the official Linux wheel’s linkage and optimisation, and other backends are untested. The [msgspec receipt](msgspec-valid-feedback.json) records stable input-dependent feedback from its own `_core.c` decoder, including 35 differing features in the JSON decoder section. The source build uses clang -O0 while the published wheel is built with GCC; only untyped `type=Any` decoding is tested. The [ujson receipt](ujson-valid-feedback.json) checks that `ujson.loads` on bytes and on text gives the exact type-tagged tree of an independent CPython `json` oracle for both controls, and records stable differential feedback in `decode.c` and double-conversion C++. Duplicate keys (last wins), integer overflow to arbitrary precision and the non-RFC `NaN`/`Infinity` tokens are documented from source only. The [python-rapidjson receipt](python-rapidjson-valid-feedback.json) checks that `rapidjson.load` on a `BytesIO` stream, and `rapidjson.loads` on bytes and on text, give the exact type-tagged CPython `json` oracle tree for both controls. Its feedback is stable on repeats and differs between the controls by 41 features in RapidJSON `reader.h`. RapidJSON header lines (242, of which 190 in `reader.h`) and `rapidjson.cpp` wrapper lines (255) are counted separately. It shares the Tencent RapidJSON C++ family with the [C++ RapidJSON path](../../cpp/json/ranking.md), at a later upstream revision, so it is not an independent parser. Under the default `number_mode`, numbers bypass RapidJSON's `strtod` and are converted by CPython. Duplicate keys (last wins), `NaN`/`Infinity` acceptance and unvalidated UTF-8 in byte streams are documented from source only. The [pysimdjson receipt](pysimdjson-valid-feedback.json) checks that `Parser().parse` on bytes and `Parser().load` on a path give the exact type-tagged tree of the CPython `json` oracle for both controls, with stdlib JSON decoding disabled during those runs. On linux/arm64 the build compiles simdjson's arm64 and fallback kernels; runtime dispatch selects `arm64` (ARM NEON) and no fallback-kernel line runs. Cython-generated wrapper lines and simdjson lines are counted separately; the wrapper feedback is identical on both controls, and all 98 differing features are in simdjson's arm64 kernel. This is the same simdjson family as the [C++ simdjson pilot](../../cpp/json/ranking.md), which pins 5.0.4 while pysimdjson 8.0.0 vendors 5.1.1. Integers beyond 64 bits raise `ValueError` and duplicate keys keep the last value; both come from source and docs, not tests. The simplejson metric is retained in the dated [lead snapshot](leads.json). The [json5 receipt](json5-valid-feedback.json) checks that `json5.loads` on bytes and on text, and `json5.load` on a `BytesIO` stream, give the exact type-tagged CPython `json` oracle tree for both controls; the standard `json` module is blocked during those runs and json5 never imports it. Docker line tracing covers 668 json5 lines (596 in the glop-generated `parser.py`, 72 in `lib.py`). Three runs per control give identical feedback, and the controls differ by 27 `parser.py` lines and 27 AFL++ tuples. json5 is a JSON5 superset parser: it accepts comments, unquoted keys, trailing commas, single-quoted strings, hexadecimal numbers and Infinity/NaN, so it does not reject non-RFC 8259 input, and its downloads mainly reflect JSON5 configuration use. Duplicate keys (last wins by default) and number conversion through Python `int`/`float` come from source, not tests. The [CPython `json` standard API](standard.json) is recorded separately, without a third-party popularity rank.

The Pydantic and jiter LLVM exports warned about mismatched profile data in 99 and 16 whole-extension functions respectively. Their coverage claims are limited to the scoped Jiter regions recorded in the verification receipts; complete extension coverage is not established.
