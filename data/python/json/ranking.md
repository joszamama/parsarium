# Python × JSON: pilot ranking

Eight third-party paths are control verified so far; nine targeted documentation leads were recorded, and one remains unverified. The ten-path ceiling is not a quota. The bounded PyPI Simple Index search is pending, so this is not a claim about the definitive most-used JSON parsers.

The comparable within-cell signal is [PyPI Stats](https://pypistats.org/api/) `last_month` package downloads excluding known mirrors, observed 2026-11-17 around 02:24 UTC. It measures adoption of entire packages, including transitive installs and uses unrelated to JSON parsing. Unverified leads are recorded in [leads.json](leads.json) but are not ranked as verified parsers.

The standalone `jiter` package is a distinct verified package API path, not an independent parser: it shares Pydantic's Jiter Rust parser family (0.19.0 standalone, 0.18.0 inside pydantic-core). Their package download metrics remain separate. The [jiter receipt](jiter-valid-feedback.json) records exact valid-control type-tagged trees and repeated, input-dependent feedback in Jiter's own Rust parser source. All eight selected paths have pinned container controls, parser-scoped coverage, and AFL++ feedback. The [Pydantic native receipt](pydantic-valid-feedback.json) checks repeated, input-dependent Jiter source regions on two valid controls. The [orjson receipt](orjson-valid-feedback.json) records 114 differing Rust deserializer features and AFL++ tuples between those controls; vendored yyjson C syntax-parser source is outside that coverage. The [ijson receipt](ijson-valid-feedback.json) records stable valid-control differential in its own C extension and pinned YAJL C tokenizer. Its source-built embedded YAJL -O0 route differs from the official Linux wheel’s linkage and optimisation, and other backends are untested. The [msgspec receipt](msgspec-valid-feedback.json) records stable input-dependent feedback from its own `_core.c` decoder, including 35 differing features in the JSON decoder section. The source build uses clang -O0 while the published wheel is built with GCC; only untyped `type=Any` decoding is tested. The [ujson receipt](ujson-valid-feedback.json) checks that `ujson.loads` on bytes and on text gives the exact type-tagged tree of an independent CPython `json` oracle for both controls, and records stable differential feedback in `decode.c` and double-conversion C++. Duplicate keys (last wins), integer overflow to arbitrary precision and the non-RFC `NaN`/`Infinity` tokens are documented from source only. The [python-rapidjson receipt](python-rapidjson-valid-feedback.json) checks that `rapidjson.load` on a `BytesIO` stream, and `rapidjson.loads` on bytes and on text, give the exact type-tagged CPython `json` oracle tree for both controls. Its feedback is stable on repeats and differs between the controls by 41 features in RapidJSON `reader.h`. RapidJSON header lines (242, of which 190 in `reader.h`) and `rapidjson.cpp` wrapper lines (255) are counted separately. It shares the Tencent RapidJSON C++ family with the [C++ RapidJSON path](../../cpp/json/ranking.md), at a later upstream revision, so it is not an independent parser. Under the default `number_mode`, numbers bypass RapidJSON's `strtod` and are converted by CPython. Duplicate keys (last wins), `NaN`/`Infinity` acceptance and unvalidated UTF-8 in byte streams are documented from source only. The simplejson metric is retained in the dated [lead snapshot](leads.json). The [CPython `json` standard API](standard.json) is recorded separately, without a third-party popularity rank.

The Pydantic and jiter LLVM exports warned about mismatched profile data in 99 and 16 whole-extension functions respectively. Their coverage claims are limited to the scoped Jiter regions recorded in the verification receipts; complete extension coverage is not established.
