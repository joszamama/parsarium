# C++ × XML: selected parsers

10 control-verified third-party paths selected from five named format-specific libraries and a Debian `-dev` package lookup. The ceiling is ten; the selection is not padded. A path is an API or package route, not necessarily an independent parser engine.

## Primary within-cell adoption metric

Debian popcon installations of each library's `-dev` package(s) (`by_inst`), captured 2026-11-17 ([snapshot](registry-snapshot.json)). The search is a bounded comparison of five C++ XML parser libraries: tinyxml2, pugixml, Xerces-C++, libxml++ and RapidXML (RapidXML measured from the same saved popcon snapshots). On 2026-11-18 the same snapshot was searched for other C++ XML `-dev` and framework packages ([lookup](registry-snapshot.json), `debian_dev_package_search`); TinyXML (version 1), cxxtools and gSOAP (through its DOM route) come from it. An extension of that lookup to further C++ XML `-dev` packages of the same snapshot (`round_4_extension`) gives OpenSP and libcutl, and a search of the descriptions of all Debian sid `-dev` packages mentioning XML (`round_4_description_search`, [rows](registry-snapshot.json)) adds none. The cell is at its ten-path ceiling.

The seven namespace-measured paths give the same structure on the catalog control; OpenSP and cxxtools are measured as raw-name paths. Xerces-C++, pugixml, TinyXML, libxml++, gSOAP, RapidXML and libcutl also pass the shared order control; TinyXML2 rejects its processing instruction, so the TinyXML2 path uses a second valid order control with only that instruction removed. pugixml, TinyXML, TinyXML2, and RapidXML preserve qualified names; adapter code resolves namespaces. RapidXML's default parse flags skip the processing instruction rather than rejecting it, so it uses the shared order control unchanged. libxml++ delegates actual parsing to libxml2. Its Docker build instruments the wrapper and the pinned libxml2 source; a parser-only probe shows stable, input-dependent AFL++ feedback and different covered `parser.c` lines across the two valid controls.

Xerces-C++ uses its own scanner. Its [parser-only probe](../../../projects/xml/cpp/xerces_c/parser-probe.cpp) calls `XercesDOMParser::parse` without DOM traversal or result formatting; the two valid controls differ by 274 stable scanner source lines and 473 repeat-stable AFL++ tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/xerces_c/differential.json)). The full harness separately checks the namespace-aware tree output.

RapidXML's documented `xml_document<>::parse<0>(char*)` parses in situ: it writes into the caller's buffer, which must be mutable and zero-terminated, so the adapter parses a copy. Its [parser-only probe](../../../projects/xml/cpp/rapidxml/parser-probe.cpp) calls only `parse<0>` with an AFL++ allowlist limited to `rapidxml.hpp`. The two valid controls give 38 and 45 repeat-stable tuples, a difference of 15, and 329 versus 374 covered header lines ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/rapidxml/differential.json)); the full control run covers 413 `rapidxml.hpp` lines. Boost.PropertyTree's XML reader embeds a RapidXML-derived copy and is not counted as a separate engine: Boost 1.90.0's `detail/rapidxml.hpp` matches 84.2% of RapidXML 1.13's normalized non-trivial lines in sequence.

TinyXML 2.6.2 is the last upstream release of the original TinyXML, pinned as Debian's unmodified orig tarball (SHA-256 `15bdfdcec58a7da30adc87ac2b078e4417dbe5392f3afb719f9ba6d062645593`) and built with `TIXML_USE_STL` as Debian builds it; Debian's CVE and entity-encoding patches, which concern malformed input and output escaping, are not applied. It is a different code base from TinyXML2: only 51 of 1,698 normalized non-trivial lines of `tinyxmlparser.cpp` and `tinyxml.cpp` match `tinyxml2.cpp` in sequence (3.0%). `TiXmlDocument::Parse` keeps the order control's processing instruction as an unreported unknown node. The first control covers 672 TinyXML lines (449 in `tinyxmlparser.cpp`); the two valid controls differ by 160 covered source lines and 172 repeat-stable AFL++ tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/tinyxml/differential.json)).

cxxtools 3.0.0 (Debian's orig tarball, SHA-256 `07b18037fb0983f6292f5c8d53e2369e9e7a9711df2c9ad50838aacbc8c62f7c`, LGPL-2.1-or-later) is a general C++ utility library whose `cxxtools::xml::XmlReader` is its own state-machine parser over cxxtools' Unicode streams. `XmlReader` reports names as written and keeps `xmlns` declarations as attributes; its `StartElement` has a namespace context that the reader never fills. It is therefore a **raw-name path**, checked against the same expat non-namespace oracle as the C raw-name paths, on both shared controls unchanged. The build force-includes `<ctime>` (current libstdc++ no longer provides `struct tm` to `timer.cpp`) and has OpenSSL headers only. The first control covers 717 libcxxtools lines, 478 of them in `xml/xmlreader.cpp`; the controls differ by 237 covered lines (177 in `xmlreader.cpp`) and 123 repeat-stable AFL++ tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/cxxtools/differential.json)). Its 42 dev installations are a weak signal for a utility library, not XML-specific use.

gSOAP 2.8.142 (Debian's orig tarball, SHA-256 `8ae3bbd57c7855e53b436eacd48ee3d297545fc974c0717dd98903d6f1840f65`, GPL-2.0) is a SOAP/REST web-services toolkit with its own XML engine (`stdsoap2.cpp`) and a DOM parser (`dom.cpp`). Its DOM manual documents a DOM-only build: run gSOAP's `soapcpp2 -CSL import/dom.h` once and link the generated `soapC.cpp` with `dom.cpp` and `stdsoap2.cpp`; the harness then reads an `xsd__anyType` with `operator>>` from a `std::istream` (`SOAP_C_UTFSTRING | SOAP_DOM_TREE`). gSOAP resolves namespaces itself: every DOM element and attribute carries its URI, and the `xmlns` declarations stay as DOM attributes, so both shared controls give the exact namespace-aware summary without adapter-side resolution. The generated serializer boilerplate is built outside the measured sources. The first control covers 1,648 gSOAP lines (1,501 in `stdsoap2.cpp`, 147 in `dom.cpp`); the controls differ by 126 covered lines, all in `stdsoap2.cpp`/`stdsoap2.h`, and 84 repeat-stable AFL++ tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/gsoap/differential.json)). The fuzz target disables only UBSan's alignment check, because gSOAP's allocator stores a canary at unaligned offsets on every valid parse. Its 95 dev installations count the whole toolkit, not XML-parser use.

OpenSP 1.5.2 (Debian's orig tarball, SHA-256 `334c444c97590a000f20bcef7c1bec63d4e396bae6ba48b3ff49596443c467dd`, MIT) is the OpenJade team's continuation of James Clark's SP SGML parser. Its `doc/xml.htm` documents parsing XML with the XML SGML declaration: the `pubtext/xml.soc` catalog, `SP_CHARSET_FIXED=YES`, `SP_ENCODING=XML`, and the `xml` and `no-valid` warning options. The harness sets exactly these through the documented generic API (`ParserEventGeneratorKit`, `EventGenerator::run`, `SGMLApplication` callbacks) over the local bytes written to a private temporary file. SGML has no Namespaces in XML, so OpenSP is a **raw-name path** checked against the expat non-namespace oracle, on both shared controls unchanged. Without a DTD it implies an attribute list per element type and reports attributes in that order; the harness keeps only the attributes specified in each start tag, which is source order on these controls but not in general. The 2005 sources use C++98 access declarations that clang rejects in later modes, so `libosp` is built as `gnu++98`. The first control covers 7,846 `libosp` lines (233 in `parseInstance.cxx`); the controls differ by 575 covered lines and 326 repeat-stable AFL++ tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/opensp/differential.json)). Its 82 dev installations (runtime `libosp5` 10,165, mostly SGML/DocBook tool chains) are not XML-specific use.

libcutl 1.10.0+ds1 (Debian's orig tarball, SHA-256 `957e9cf366501577bcdbc160a0bcb4eeeea9ba0d21de104340b861622c17218b`, MIT) is Code Synthesis' C++ utility library. Its `cutl::xml::parser`, documented in `cutl/xml/parser.hxx`, turns Expat's namespace-mode callbacks into pull events; Debian's repack removes the bundled Expat subset and builds against the system Expat, so the harness links the pinned Expat 2.10.0 (the C cell's release) and compiles only the `cutl/xml` component. Element and attribute names come from the parser's qnames and declarations from its `start_namespace_decl` events, so both shared controls give the exact namespace-aware summary. This is an **Expat-family wrapper**: the cutl layer's covered lines differ by only 6 between the controls (`cutl/xml/parser.cxx`), Expat's by 567, and the AFL++ maps by 162 repeat-stable tuples ([feedback receipt](../../../fuzzing/afl-native/xml/cpp/libcutl/differential.json)). Because `cutl::xml::parser` creates the Expat parser internally and has no `XML_SetHashSalt` hook, the harness supplies a fixed `arc4random_buf` (used only by Expat's salt), as the C expat path fixes the salt; without it the order control's map varied between runs. Its 3 dev installations, none with recent use, are a very weak signal; the same API was later split out as libstudxml, which has no Debian package.

## Standard API (unranked)

None. The ISO C++ working draft and cppreference's header index contain no XML header ([evidence](standard.json)).

## The metric is close

Homebrew install-on-request (365 days) orders the four libraries differently: tinyxml2 1,757, pugixml 1,270, Xerces-C++ 1,209, libxml++ 461. Debian dev installs, the one primary metric, put Xerces-C++ first by a wide margin (2,676 vs 1,503 for pugixml) and pugixml second, ahead of tinyxml2 (487). On Homebrew, tinyxml2 would lead and Xerces-C++ would be third; that order is a caveat, not a second ranking. RapidXML's 17 is a weak signal: all 17 `librapidxml-dev` installations report no recent use, and the count measures only the Debian package, not copies vendored into projects or embedded in Boost. It ranks ninth, and libcutl's 3 tenth, because the protocol keeps positive primary-metric paths in descending order without a minimum. RapidXML has no Homebrew formula. gSOAP's Homebrew formula (2.8.147) had 282 and OpenSP's `open-sp` (1.5.2) 65 installs on request over 365 days when looked up on 2026-11-18. The 275 libxml++ dev installations sum `libxml++2.6-dev` (266), `libxml++-4.0-dev` (2), and `libxml++-5.0-dev` (7). Only the last matches the verified ABI-5 release family. Homebrew's 461 corresponds to its older 2.42.4 formula. Source-level popcon is not used: libxml++2.6's 79,794 is a runtime package pulled in by dependents, and 79,361 of those installs show no recent file access.

## Search limit

The bounded search compared five named, format-specific C++ XML libraries and then looked up C++ XML `-dev` and framework packages in the same popcon snapshot. Xalan-C++, XQilla, CodeSynthesis XSD and XMLTooling run over Xerces-C++; gdome2's C++ wrapper runs over libxml2; Arabica (2; a wrapper over expat, libxml2 or Xerces-C++), ACEXML (1; ACE's own SAX parser) and gxmlcpp (2; a libxml2 wrapper) rank below the tenth path and were not built; ACE's XML_Utils (3) run over Xerces-C++; libstudxml has no Debian package. The description search found no other C++ XML parser `-dev` package with more than three installations: the remaining rows are XML-RPC, property-list, mzML, SCXML, UI or code-generation libraries. Other C++ XML packages may exist and their adoption remains unmeasured here. The two small valid controls do not establish complete XML 1.0, DTD/entity, encoding, or malformed-input behavior. No standard-library XML API was found in the official inventory.

Qt XML, Boost.PropertyTree and POCO XML are parts of larger frameworks and are not ranked by whole-framework installs. Qt Core `QXmlStreamReader` and POCO XML `SAXParser` both passed local control and feedback checks but are not selected: Qt has only the framework-wide `qt6-base-dev` count (4,942), and POCO's XML-specific runtime package has 887 installations, below the 1,000 format-specific fallback ([leads](leads.json)). POCO XML also shares the Expat family.
