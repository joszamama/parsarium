# C++ × JSON: selected parsers (pilot)

Ten control-verified third-party paths are selected: nine ranked by the primary metric, plus Boost.JSON, whose multi-library source package lacks a JSON-specific primary value and which is kept by its JSON-specific `libboost-json-dev` fallback count. POCO JSON passed verification but was demoted for lack of a qualifying metric. All ten slots are used; the Qt lead is excluded because it has no qualifying metric. The last three ranks rest on very small installation counts.

## Adoption metric

The ranking uses Debian popcon `sourcemax/by_inst` installations: the maximum over binary packages built from each C++ JSON source package. The [snapshot](registry-snapshot.json) was captured 2026-11-17 from 320 Debian source-name hits. Counts are a package adoption proxy, not JSON-specific use, and favor libraries with runtime packages.

The source-package order differs from the dev-package view: simdjson is a runtime dependency for other Debian software, while nlohmann/json is header-only. GitHub stars are a separately recorded signal and not combined with popcon: nlohmann/json 50,894, simdjson 24,576, JsonCpp 8,916, boostorg/json 482 at the recorded snapshot. No ordering here establishes the definitive most-used C++ JSON parser.

RapidJSON v1.1.0 uses `Document::Parse(const char*, size_t)` on local bytes. Its parser headers are MIT; third-party examples/tests in the source archive are not compiled. The older release needs Clang's `-fdelayed-template-parsing` on the pinned toolchain, without a source patch. Its AFL++ target uses AddressSanitizer and source coverage, without UndefinedBehaviorSanitizer. Both valid controls pass with stable, input-dependent parser-line and AFL++ feedback.

simdjson uses its [documented DOM pointer-and-length input API](https://github.com/simdjson/simdjson/blob/v5.0.4/doc/dom.md), which copies to a padded buffer. The v5.0.4 [source archive](https://github.com/simdjson/simdjson/releases/tag/v5.0.4) is pinned by SHA-256 `827417bcf88309df170962e7bd1b4b4a4992d5d4e5cb82a0442ada9530e916d2` and includes Apache-2.0 and MIT licenses. The Docker harness compiles the pinned singleheader amalgamation with LLVM coverage and AFL++. The full DOM printed from each of the two valid controls matches the control's nested JSON value. Source lines and AFL tuples are repeatable in two replays of each control; the controls differ by 166 source lines and 330 AFL tuples ([feedback](afl-feedback.json)). The base control covers 984 `simdjson.cpp` and 380 `simdjson.h` lines. These are own-library lines, not harness lines.

Boost.JSON has no primary rank. Its Debian source package, `boost1.83`, builds every Boost library, so its sourcemax count (100,348) is not JSON-specific and cannot be compared with the single-library sources above. The only number used for it is a separately labeled fallback: 1,749 `libboost-json-dev` installations from the same hashed `by_inst` file. It compares only with the dev-install column, not with source installations. The runtime package `libboost-json1.83.0` has 1,798 installations; it is recorded in the [snapshot](registry-snapshot.json) and not ranked.

Boost.JSON 1.92.0 comes from the official [Boost release archive](https://github.com/boostorg/boost/releases/tag/boost-1.92.0), pinned by SHA-256 `ea7b982002cc9dfbe59b0b217b206f470dc75f3de0bb2973d844118934d82411` (BSL-1.0). The harness calls the [documented](https://www.boost.org/doc/libs/1_92_0/libs/json/doc/html/ref/parse.html) `boost::json::parse(string_view, error_code&)` with default strict options and builds header-only through `boost/json/src.hpp`. Only `boost/json` headers count as parser source; the other Boost headers it includes are compiled but not counted. For each valid control, the DOM printed by the harness equals Python's `json.loads` result, including key order and integer/float kinds. The base control covers 1,601 Boost.JSON lines, including 552 in `basic_parser_impl.hpp`. Lines and AFL tuples repeat across two replays per control; the controls differ by 140 source lines and 103 AFL tuples ([feedback](afl-feedback.json)).

cpprestsdk 2.10.19, the Microsoft C++ REST SDK, is pinned from its newest [release tag archive](https://github.com/microsoft/cpprestsdk/releases/tag/v2.10.19) by SHA-256 `4b0d14e5bfe77ce419affd253366e861968ae6ef2c35ae293727c1415bd145c8` (MIT). The upstream README says the SDK is in maintenance mode and not recommended for new projects. The harness calls the [documented](https://github.com/microsoft/cpprestsdk/blob/v2.10.19/Release/include/cpprest/json.h) `web::json::value::parse(const utility::string_t&)` on local bytes; on Linux `utility::string_t` is `std::string`. By default the parser sorts object members by key. The harness first calls the documented global `web::json::keep_object_element_order(true)`, which keeps them in source order. For each valid control, the printed tree equals Python's `json.loads` result, including key order and integer/float kinds. Only the three JSON translation units (`json.cpp`, `json_parsing.cpp`, `json_serialization.cpp`) and the UTF/locale helpers in `asyncrt_utils.cpp` are compiled. A small `stdafx.h` shim replaces the library's precompiled header, which pulls in the HTTP, websocket and Boost.Asio headers. No cpprest source file is changed. The base control covers 427 lines of those JSON units, 407 of them in `json_parsing.cpp`. The parser-only AFL++ probe calls `value::parse` without traversal or serialization. Its allowlist names only the three JSON units, and the build checks with `nm` that exactly those objects carry AFL++ instrumentation. Three runs per control repeat exactly. The controls differ by 11 parser lines and 25 of 147/134 AFL tuples ([receipt](../../../fuzzing/afl-native/json/cpp/cpprestsdk/differential.json)). Its rank rests on 813 installations of the Debian `cpprest` source package, found by a supplementary exact source-name lookup in the same hashed snapshot (see the [snapshot](registry-snapshot.json)). The source builds one library, so the primary count applies. That library also covers HTTP, URIs, websockets and streams, so the count is not JSON-specific. The split between `libcpprest2.10` and `libcpprest-dev` is not in the saved snapshot.

Glaze 9.1.0 is pinned from its [official release tag](https://github.com/stephenberry/glaze/releases/tag/v9.1.0) by SHA-256 `55f8a675397c505f9bee6c160e1c26b0085868f185d04d7a7727531fdbff4bd4` (MIT). Its documented `glz::read_json(glz::generic_i64&, std::string)` reads local bytes into an insertion-ordered generic DOM with signed integers and doubles. The replay of each valid control matches the original nested structure, key order, and integer/float kinds. The base control covers 1,623 Glaze source lines, including 415 in `json/read.hpp`. The parser-only AFL++ probe calls `read_json` without serialization or DOM traversal; its feedback repeats exactly and differs by 25 reader lines and 140 AFL tuples between controls ([receipt](../../../fuzzing/afl-native/json/cpp/glaze/differential.json)). The primary 171-installation source count comes from a supplementary exact `glaze` source-name lookup in the *same hashed Debian snapshot* as the other rows. Glaze was not one of the 320 source names containing `json`; its `libglaze-dev` binary count is also 171.

PicoJSON 1.3.0 is pinned from its [release tag archive](https://github.com/kazuho/picojson/releases/tag/v1.3.0) by SHA-256 `056805ca2691798f5545935a14bb477f2e1d827c9fb862e6e449dbea22801c7d` (BSD-2-Clause). The harness calls the [documented](https://github.com/kazuho/picojson/blob/v1.3.0/README.mkdn) two-argument `picojson::parse(picojson::value&, const std::string&)` on local bytes. It is built with the documented `PICOJSON_USE_INT64` option, so integers stay `int64_t` and other numbers stay `double`. `picojson::value::object` is a `std::map`, and 1.3.0 has no ordered mode, so the parsed tree lists keys in sorted order and cannot keep the control's key order. For each valid control, the printed tree equals Python's `json.loads` result with the same array order and integer/float kinds; object members are compared by key, not by position. The base control covers 301 `picojson.h` lines. The parser-only AFL++ probe calls `picojson::parse` without traversal or serialization. Its allowlist adds `fun:_ZN8picojson*`, because a file-only `src:picojson.h` allowlist gave a 145-site map against 579 with the function entries. Three runs per control repeat exactly. The controls differ by 8 parser lines and 37 of 156/139 AFL tuples ([receipt](../../../fuzzing/afl-native/json/cpp/picojson/differential.json)). Its rank rests on 16 Debian installations of the `picojson` source package (1 vote, 15 old, 0 recent), whose only binary is `picojson-dev`. That is a weak package proxy, and the 1.3.0 release dates from 2015.

jsoncons 1.10.0 is pinned from its [release tag archive](https://github.com/danielaparker/jsoncons/releases/tag/v1.10.0) by SHA-256 `c829350a2eece662beb378143e2ab1c1cbb07d703687bf168626665a8a7d8bc1` (BSL-1.0). The harness calls the [documented](https://github.com/danielaparker/jsoncons/blob/v1.10.0/doc/ref/corelib/json/parse.md) `jsoncons::ojson::parse(const char*, size_t)` on local bytes. [`ojson`](https://github.com/danielaparker/jsoncons/blob/v1.10.0/doc/ref/corelib/ojson.md) keeps object insertion order; the default `json` type sorts keys, so it would not match the control's key order. For each valid control, the printed tree equals Python's `json.loads` result, including key order and integer/float kinds. The base control covers 726 lines in jsoncons' own `json_parser.hpp` (2,416 jsoncons lines in all). The parser-only AFL++ probe calls `ojson::parse` without serialization; its allowlist names the `basic_json_parser` methods, because a file-only allowlist skipped parser functions whose first instruction is inlined from another header and left a 60-site map. Three runs per control repeat exactly. The controls differ by 76 parser lines and 41 of 164/155 AFL tuples ([receipt](../../../fuzzing/afl-native/json/cpp/jsoncons/differential.json)). Its rank rests on 3 Debian installations (1 recent) of the `jsoncons` source package, whose only binary is `libjsoncons-dev`. That is a very weak package proxy, not evidence of JSON-specific use; jsoncons also reads CBOR, BSON, MessagePack, CSV and other formats. GitHub stars (859 in the saved lead) are a different metric and are not combined.

taoJSON 1.0.0-beta.14 is pinned from its [tag archive](https://github.com/taocpp/json/releases/tag/1.0.0-beta.14) by SHA-256 `f9e44a1d6a70a6d39b9e45df76eac928e69f5318e5a957fd5c0efdf45dacaf5e` (MIT). Every taoJSON tag is a GitHub pre-release; this is the newest, and no final 1.0.0 exists. The tag pins PEGTL as a git submodule at the 3.2.6 release commit. The harness fetches that [PEGTL 3.2.6 archive](https://github.com/taocpp/PEGTL/releases/tag/3.2.6) separately, pinned by SHA-256 `0ad229e47e5e865c90788bb9865447804c72dcb171b7402f6f0fe8c78f3b2035` (MIT). The harness calls the [documented](https://github.com/taocpp/json/blob/1.0.0-beta.14/doc/Batteries-Included.md) `tao::json::from_string(const char*, std::size_t, source)` on local bytes. Like PicoJSON, `tao::json::value` stores objects in a `std::map`. Each control therefore matches Python's `json.loads` with the same array order and integer/float kinds, with object members compared by key. The base control covers 341 taoJSON lines, including 52 in its JSON `grammar.hpp`, plus 389 PEGTL engine lines counted separately as underlying parser source. The parser-only AFL++ probe calls `from_string` without traversal or serialization. Its allowlist names the `tao::json` and `tao::pegtl` functions; file entries alone gave an 834-site map against 1,984. Three runs per control repeat exactly. The controls differ by 34 parser lines and 166 of 344/292 AFL tuples ([receipt](../../../fuzzing/afl-native/json/cpp/tao-json/differential.json)). taoJSON was found by re-scanning the 320 recorded source-name hits; the other positive hits that were not yet decided are C libraries, schema validators, bindings, or non-C++ projects (see the [snapshot](registry-snapshot.json)). Its rank rests on 2 Debian installations of the `tao-json` source package, both classified `no_files`, with 0 votes and 0 recent. Debian ships a 2020 git snapshot rather than this tag. This is the weakest adoption signal in the cell and does not show JSON-specific use.

POCO JSON 1.15.4 passed the same technical gate (both exact-tree controls through `Poco::JSON::Parser::parse(std::string)`, coverage in `ParserImpl.cpp` and bundled `pdjson.c`, stable parser-only AFL++ feedback) but is not selected. Its Debian source `poco` (940) covers the whole suite, `libpoco-dev` (190) is suite-wide, and the JSON runtime `libpocojson100` (125, all `no_files`) is below the 1,000 format-specific fallback in PROTOCOL.md. The project, overlay and records are archived in [poco-json-demoted.json](poco-json-demoted.json).

## Excluded and unresolved leads

| Lead | Source installs | Dev installs | Status |
| --- | ---: | ---: | --- |
| [POCO JSON](https://docs.pocoproject.org/current/Poco.JSON.Parser.html) | unavailable (POCO-wide 940) | 190 (suite) / 125 runtime | Verified technically; excluded: no JSON-specific metric at or above the 1,000 fallback |
| [Qt QJsonDocument](https://doc.qt.io/qt-6/qjsondocument.html) | unavailable (Qt-wide 96,909 / 67,857) | none JSON-specific (qt6-base-dev 4,942 framework-wide) | Excluded: no JSON-specific metric for the 1,000 fallback; not control-tested |

Qt QJsonDocument cannot qualify, whatever the outcome of its build blocker. It lives in QtCore, so the Debian sources `qtbase-opensource-src` and `qt6-base` count whole frameworks and are format-ambiguous. The PROTOCOL.md fallback then needs a JSON-specific binary development package with at least 1,000 installations. Qt has none: `qt6-base-dev` (4,942) covers the Qt base framework and `libqt6core6t64` covers all of QtCore. The decision and the earlier link blocker are in [qt6-jsondocument-unresolved.json](qt6-jsondocument-unresolved.json).
