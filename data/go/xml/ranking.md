## Standard API (unranked)

| API | Runtime | Parser family |
| --- | --- | --- |
| [encoding/xml.Decoder.Token()](https://pkg.go.dev/encoding/xml@go1.27.1#Decoder.Token) | Go 1.27.1 | Go encoding/xml Decoder tokenizer |

etree reads through `encoding/xml.Decoder.RawToken`; xmlquery, mxj, x2j, goxpp and go-pkg-xmlx read through `encoding/xml.Decoder.Token`. Those six third-party paths and the standard API share one runtime tokenizer. govmomi/vim25/xml contains a separately compiled tokenizer fork derived from Go encoding/xml source. etree and xmlquery each build their own trees; mxj and x2j build maps; goxpp maintains a pull cursor with depth and namespace state; go-pkg-xmlx builds a node tree. gokogiri and lestrrat-go/libxml2 are two cgo bindings over the same native libxml2 build, and helium is an independent pure-Go parser. mxj's 553 counts only the v1 module path; the v2 successor module (178) is excluded as the same parser path (86.6% source overlap).

x2j has no tagged release; it is pinned at the only proxy pseudo-version, a GitHub fork of `github.com/clbanning/x2j` frozen in 2013 by the author who later wrote mxj. Its 436 importers count only the beego fork path, likely mostly older beego code; the upstream `github.com/clbanning/x2j` (47) is excluded as the same parser path (x2j.go matches 626 of 643 lines). Its `Unmarshal`, `ByteDocToMap` and `DocToMap` run the regular expression `[ \t\n\r]*<` over the raw document before tokenizing, so the catalog control's CDATA `x < y` comes back as `x< y`. `ToMap(io.Reader)` skips that step and keeps indentation as `#text` entries. An expat projection onto the map fields ([oracle check](x2j-oracle-check.json)) matches the reader map on both controls and the byte map everywhere except that CDATA value. Its AFL++ bridge maps x2j blocks, and a second probe through the same harness maps encoding/xml blocks; both repeat exactly, but x2j's own blocks differ between the two controls by one block (the nested-map branch at x2j.go:315), against 30 encoding/xml blocks. `encoding/xml` itself shows 79,507 importers but stays outside the third-party ranking.

goxpp uses the documented `NewXMLPullParser(io.Reader, true, nil)` and `NextToken()` API on local byte streams. Its two valid controls match the namespace-aware expected summaries. The catalog control covers 84 goxpp source lines and 306 underlying `encoding/xml` lines. Its own AFL++ blocks repeat identically per control and differ by three between controls, all in comment event handling; a separate `encoding/xml` trace differs by 32 blocks. The 132 importers rank sixth among verified paths.

govmomi/vim25/xml exposes the general `NewDecoder(io.Reader).Token()` API. The pinned `v0.56.2` Docker build matches both namespace-aware control summaries and covers 290 lines in its own forked `xml.go`. Parser-only AFL++ traces repeat identically per control and differ by 30 source blocks and 30 tuples; every changed block is in `xml.go`. The source lock pins the 12,553,438-byte whole govmomi module archive. Its 163 Imported by count is for the `vim25/xml` package and ranks fifth among verified paths; it is not an XML-call count.

gokogiri's `xml.Parse([]byte)` cgo route builds a DOM through native libxml2. Both namespace-aware controls match the independently specified summaries. The first covers 93 Go binding lines and 1,730 libxml2 parser lines. The AFL++ target instruments only `parser.c`, `parserInternals.c`, and `entities.c`; full and parse-only maps are identical, so DOM traversal contributes no tuples. Five repeats per control are stable, with 364 tuple IDs differing between the two valid controls. It shares the libxml2 parser family counted in C and C++ and is ranked by its Go package's 108 importers, not by libxml2 adoption.

lestrrat-go/libxml2's `libxml2.Parse([]byte, parser.XMLParseNoNet)` calls `xmlCtxtReadMemory` through its own cgo `clib` layer and wraps the result in its own `types`/`dom` node API, separate from gokogiri's. Both namespace-aware controls match the expat oracle summaries. The catalog control covers 197 Go binding lines and 1,789 libxml2 parser lines. It links the same pinned libxml2 2.15.4 static build as gokogiri; the AFL++ target instruments only `parser.c`, `parserInternals.c` and `entities.c`, full and parse-only maps are identical, five repeats per control are stable, and 368 tuple IDs differ between the controls ([receipt](../../../fuzzing/afl-native/xml/go/github_com_lestrrat_go_libxml2/feedback-validation.json)). This is shared-parser feedback; the binding's own code is measured only as source coverage. The 2026-07 pseudo-version needs a one-line cgo type change (`cgo-compat.patch`) to compile against libxml2 2.15 headers. The upstream README marks the repository archived and points to helium; the pre-rename `github.com/lestrrat/go-libxml2` path (9) is not counted.

go-pkg-xmlx's `Document.LoadBytes([]byte, nil)` runs `LoadStream`, which builds its own node tree (element, text, comment, directive and processing-instruction nodes) from `encoding/xml.Decoder.Token`. Both namespace-aware controls match the expat oracle summaries. The catalog control covers 44 package lines (`document.go`, `node.go`) and 294 underlying `encoding/xml` lines. Its own AFL++ blocks repeat per control and differ by two between controls, the comment and processing-instruction node branches; a separate `encoding/xml` trace differs by 30 blocks ([receipt](../../../fuzzing/afl-native/xml/go/github_com_go_forks_go_pkg_xmlx/differential.json)). The module has no tagged release and is pinned at its only proxy pseudo-version. It is a fork of the original jteeuwen/go-pkg-xmlx; `github.com/mattn/go-pkg-xmlx` (15) is byte-identical in all three non-test source files and is not counted.

helium's `NewParser().Parse(ctx, []byte)` is an independent pure-Go XML parser: its linked package graph has no `encoding/xml` and no cgo, and its tokenizer, reference decoding, namespace resolution and DOM builder are its own code, ported in structure from libxml2. Both namespace-aware controls match the expat oracle summaries. The catalog control covers 1,501 lines in 41 helium source files. Its AFL++ blocks repeat per control and differ by 221 source blocks and 219 tuples between the controls ([receipt](../../../fuzzing/afl-native/xml/go/github_com_lestrrat_go_helium/differential.json)). Its 12 importers tie with three other snapshot leads (printesoi/xml-go, sbabiv/xml2map, dgrr/quickxml), all excluded on overlap or control evidence.
